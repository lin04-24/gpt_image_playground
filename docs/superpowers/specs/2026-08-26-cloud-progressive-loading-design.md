# 云同步图片渐进式加载设计

日期：2026-08-26
状态：待用户审阅，未进入实现阶段

## 1. 背景与目标

当前跨浏览器云同步流程将远端快照中的全部任务和图片元数据一次返回。客户端在 `applyRemoteSnapshot` 中等待所有远端缩略图下载完成后，才把任务写入 Zustand 并显示首页。图片数量较多时，首页会被全量缩略图下载阻塞，首次打开可能需要两三分钟。

本设计把同步拆成“任务元数据分页拉取”和“缩略图渐进补齐”两条相互独立的流程：

- 新浏览器先取得按 `createdAt` 倒序排列的最新 20 个任务。
- 20 个任务的提示词、参数和任务状态立即进入首页；缩略图到达一张显示一张，未到达时显示现有占位图。
- 第 21 个及之后的任务按顺序后台取得。某任务的封面缩略图成功后才追加该任务卡；失败时追加占位卡并继续后续队列。
- 所有任务只同步元数据和缩略图。原图不参与启动或后台预取，详情、下载、复用等现有按需场景继续通过远端图片加载器取得原图。
- 搜索、状态筛选和收藏夹操作可以提升相关任务的分页请求与缩略图请求优先级。
- 同步完成后仍保持当前双向合并和冲突处理语义，不能因为客户端只加载了部分历史就覆盖或误删云端未加载数据。

## 2. 非目标

- 不改变任务卡的布局、首页排序规则、提示词展示格式或详情页交互。
- 不把原图转换成新的云端格式，也不扩大 IndexedDB 原图缓存范围。
- 不在本次工作中重写现有全量快照协议；保留它供旧版本客户端继续使用。
- 不引入新的状态管理库、分页库或网络请求依赖。
- 不将首页改为虚拟列表。若后续历史任务达到数万条，再单独评估渲染层优化。

## 3. 现有实现与可复用模块

当前相关实现如下：

- `src/components/CloudSyncGate.tsx` 在本地初始化完成后启动云同步。
- `src/lib/cloudSync.ts` 负责快照读取、任务合并、图片上传下载、冲突重试和远端原图加载器注册。
- `server/index.mjs` 保存完整任务快照，并通过 `/cloud-api/snapshot` 和 `/cloud-api/images/:id[/thumbnail]` 提供同步接口。
- `src/lib/db.ts` 已有任务、原图和缩略图的 IndexedDB 存取接口，缩略图版本为 `CURRENT_THUMBNAIL_VERSION`。
- `src/lib/imageCache.ts` 已有缩略图缓存、后台补全队列、订阅机制和远端原图按需加载机制。
- `src/components/TaskCard.tsx` 已通过 `subscribeImageThumbnail` 和 `ensureImageThumbnailCached` 支持缩略图异步更新。
- `src/components/TaskGrid.tsx` 已按 `createdAt` 倒序过滤任务，搜索与状态规则复用 `store.ts` 中的 `taskMatchesSearchQuery` 和 `taskMatchesFilterStatus`。

实现时优先扩展这些边界，不复制任务合并、缩略图缓存和原图按需加载逻辑。

## 4. 设计总览

### 4.1 同步阶段

客户端把一次云同步划分为四个阶段：

1. **获取同步基线**：读取一个带固定 `revision` 的分页快照基线，包括持久化设置、收藏夹状态、远端删除标记、对话数据和第一页任务。
2. **首屏应用**：先应用持久化设置与第一页 20 个任务，不等待任何缩略图；首屏缩略图进入高优先级队列。
3. **历史分页**：按游标取得后续任务页。每页的任务元数据写入 IndexedDB；任务的第一张输出缩略图进入后台队列。成功后逐张加入 Zustand，失败则加入占位卡并记录待重试项。
4. **完整同步收敛**：全部任务页和必要的对话数据取得后，使用完整的远端基线与当前本地变更执行现有合并和一次全量快照写回。只有这一阶段完成后，才允许普通 `schedulePush` 发送全量快照。

第一页应用和历史分页不等待原图下载。原图远端加载器在同步开始时注册，详情等调用 `ensureImageCached` 时才请求 `/cloud-api/images/:id`。

### 4.2 首屏与历史显示规则

- 排序键沿用 `TaskGrid`：`createdAt` 倒序；相同时间使用任务 `id` 倒序作为稳定的服务端和客户端 tie-breaker。
- 第一页最多 20 个任务，少于 20 个时以实际数量为准。
- 第一页任务元数据写入状态后立即显示卡片。缩略图下载成功后更新对应 `TaskCard`；没有缩略图、请求失败或尚未完成时保持现有占位图。
- 后续任务不会因为前一张图片失败而停止队列。每个任务只以 `outputImages[0]` 作为封面资源。
- 后续任务封面缩略图成功时，任务卡立即加入状态；若请求明确失败或服务端返回缩略图不存在，则加入任务卡并显示占位图，同时进入可重试队列。这样既不阻塞历史队列，也不丢失提示词记录。
- 任务卡仍由 `TaskGrid` 统一排序，因此即使缩略图完成顺序与任务时间顺序不同，最终页面顺序不会改变。
- 同一个任务在首屏、后台队列和筛选优先队列中只能出现一次；通过任务 ID 和缩略图 ID 去重。

## 5. 服务端接口设计

### 5.1 保留旧接口

无查询参数的 `GET /cloud-api/snapshot` 和现有 `PUT /cloud-api/snapshot` 保持兼容，供尚未升级的客户端使用。旧客户端继续沿用当前全量同步行为。

### 5.2 分页读取接口

新增分页读取接口，建议统一使用 `GET /cloud-api/snapshot?mode=page`，避免引入另一套同步资源命名。响应只携带任务元数据和该页任务引用图片的云端元数据，不携带图片二进制。

#### 首次请求

`GET /cloud-api/snapshot?mode=bootstrap&limit=20`

响应结构：

```ts
interface CloudBootstrapPage {
  protocolVersion: 2
  revision: number
  state: PersistedAppState | null
  tasks: TaskRecord[]
  agentConversations: AgentConversation[]
  deletedTaskIds: Record<string, number>
  deletedConversationIds: Record<string, number>
  images: CloudImage[]
  nextCursor: string | null
  totalTasks: number
}
```

其中：

- `state`、对话和删除标记只在 bootstrap 返回，用来保持现有同步语义。
- `tasks` 按 `createdAt DESC, id DESC` 排序，数量上限为服务端允许的最大页大小；服务端将客户端的 `limit` 限制在合理范围内，不能由请求方无限放大。
- `images` 只包含该页任务引用的图片，至少包括每个任务的第一张输出；为支持详情中的原图按需加载，可包含该页任务引用的全部图片元数据，但不包含数据内容。
- `nextCursor` 是不透明游标，内部绑定 `revision` 和排序位置，客户端不得自行解析或拼接。
- 对话数据可以暂时在 bootstrap 一次返回，因为它不包含图片二进制；如果实际数据量在测量中也成为瓶颈，后续按同样模式拆分页，不改变任务分页协议。

#### 后续请求

`GET /cloud-api/snapshot?mode=page&revision=<R>&cursor=<C>&limit=20`

响应结构与 bootstrap 相同，但 `state`、对话和删除标记可以省略，只返回：

```ts
interface CloudTaskPage {
  protocolVersion: 2
  revision: number
  tasks: TaskRecord[]
  images: CloudImage[]
  nextCursor: string | null
  totalTasks: number
}
```

服务端必须验证游标对应的 `revision` 仍是当前 revision：

- revision 一致：返回该页。
- revision 不一致：返回 `409`，响应包含当前 revision；客户端丢弃本轮分页结果，从新的 bootstrap 重新开始。
- cursor 非法或过期：返回 `400`，客户端从新的 bootstrap 重新开始。

服务端的分页过滤和排序必须基于同一个内存快照，避免客户端在翻页过程中读到前后不一致的任务集合。

### 5.3 搜索与筛选参数

分页接口支持可选的服务端过滤参数，用于用户操作时的前台插队：

```text
q=<url-encoded search text>
status=all|running|done|error
favorite=true|false
collectionId=<collection id>
```

语义必须与现有客户端规则一致：

- `q` 匹配任务提示词、`JSON.stringify(task.params)` 和错误文本，大小写不敏感。
- `status=error` 同时匹配任务状态为 `error` 或存在 `outputErrors` 的任务。
- `favorite=true` 匹配 `isFavorite`，指定 `collectionId` 时使用任务收藏夹 ID，并兼容旧任务只有 `isFavorite` 的默认收藏夹回退规则。
- 未提供过滤参数时按全量任务排序分页。

服务端过滤逻辑需要用固定测试样例与客户端 `taskMatchesSearchQuery`、`taskMatchesFilterStatus` 的结果做一致性测试，避免两端出现搜索结果不同。

## 6. 客户端同步架构

### 6.1 `cloudSync.ts` 的职责调整

保留当前的任务冲突合并、图片上传、原图远端加载器和全量写回逻辑，新增以下职责：

- 请求 bootstrap 和后续任务页。
- 保存本轮分页基线：`revision`、已取得的任务、图片元数据、对话和删除标记。
- 先应用第一页，再逐页应用后续任务。
- 在分页完成前禁止完整快照 push。
- 记录分页期间发生的本地新增、修改、删除，最终统一与完整远端基线合并。
- 监听在线事件，重试缩略图失败项和中断的分页任务。

建议将分页响应类型、游标状态和任务页合并辅助逻辑放在 `src/lib/cloudSync.ts` 顶部附近或新的小型 `src/lib/cloudSyncPagination.ts` 中。只有当 `cloudSync.ts` 中的分页状态明显影响可读性时才拆文件。

### 6.2 首屏应用顺序

bootstrap 成功后的顺序固定为：

1. 保存本轮 `revision` 和远端图片元数据。
2. 使用现有 `mergeRecords` 将第一页任务与当前本地任务合并。此时不能根据第一页缺失任务执行删除。
3. 应用远端 `state`，恢复设置、收藏夹、输入草稿等现有状态。
4. 把第一页任务写入 IndexedDB，并更新 `useStore.tasks`，让 20 张卡片立即渲染。
5. 把第一页封面缩略图加入高优先级下载队列；下载完成后持久化并通过现有缩略图订阅机制通知 `TaskCard`。
6. 后台请求下一页任务。

缩略图队列需要提供一个统一的“写入并发布”入口，复用 `imageCache` 已有缓存和订阅机制。不能只调用 `putImageThumbnail` 而不触发订阅，否则已经显示的卡片不会更新。

### 6.3 后续页应用顺序

每取得一页：

1. 校验页的 `revision` 与本轮基线一致。
2. 将该页任务保存到本地任务集合和 IndexedDB，但不执行全量删除。
3. 注册该页所有任务的封面缩略图请求，后台任务低优先级。
4. 每个后续任务的封面缩略图成功后，把任务加入可见任务集合并更新 Zustand；失败后把任务加入可见集合并使用占位图，同时记录重试状态。
5. 继续请求 `nextCursor`，直到为空。
6. 页数据完成后再执行一次完整的远端删除合并、孤立任务清理和最终全量 push。

为避免 Zustand 订阅误判删除：

- `knownTaskIds` 在 bootstrap 前只代表本地完整集合，不因某一页的局部状态覆盖而更新为不完整集合。
- 分页期间不能调用当前依赖“当前任务全集”的 `trackCloudDeletions` 生成删除 tombstone。
- 分页完成后才以完整任务集合更新 `knownTaskIds`，再恢复普通 `schedulePush`。

### 6.4 本地并发写入

同步期间用户仍可生成、编辑、收藏或删除任务。设计采用当前项目的时间戳合并规则：

- 本地操作正常写入 IndexedDB 和 Zustand，不因同步进行而禁用输入。
- 分页应用远端记录时，按 `updatedAt ?? finishedAt ?? createdAt` 与本地记录比较，较新的记录胜出。
- 分页完成时重新调用 `collectSnapshot`，因此同步开始后产生的本地变化也会进入最终 push。
- 若最终 `PUT /snapshot` 返回 `409`，沿用现有冲突重试流程；冲突响应如果是完整快照，则按现有逻辑重新合并，不把分页中的局部集合当作完整远端集合。

## 7. 缩略图队列与重试

### 7.1 优先级

队列分为三类，优先级从高到低：

1. 当前首屏 20 个任务的封面缩略图。
2. 搜索、状态筛选或收藏夹结果中尚未加载任务的封面缩略图。
3. 默认历史后台队列。

前台操作发生时，不取消已在传输中的请求；只调整尚未开始的任务顺序，避免浏览器中止请求产生额外失败。

### 7.2 并发

沿用 `imageCache` 当前按图片尺寸动态调整的并发思想，但云端首屏队列设置明确上限：默认最多 4 个缩略图请求，单个大尺寸缩略图时自动降低并发。后续历史队列可使用较低并发，避免占满用户当前生成图片或 API 请求的网络资源。

每个缩略图 ID 只有一个在途 Promise；首屏、后台、筛选优先队列共享去重表，防止重复请求同一资源。

### 7.3 失败处理

- 网络错误、非 2xx 响应和数据转换错误都只影响当前缩略图，不阻塞任务页或后续任务。
- 首屏任务失败时卡片已经存在，继续显示占位图。
- 后续任务失败时追加占位卡，任务提示词和参数不丢失。
- 重试使用有限指数退避，例如 1 秒、5 秒、30 秒，单轮最多 3 次；单轮耗尽后保留失败项，不继续高频请求。
- 浏览器重新上线时重置失败项的下一次尝试时间并重新入队。
- 下次完整同步或用户重新进入页面时再次检查远端缩略图是否存在。
- 原图按需加载失败仍由现有 `ensureImageCached` 行为处理，不与缩略图队列共用错误状态。

## 8. 搜索、筛选和收藏夹

现有 `TaskGrid` 对 `useStore.tasks` 做本地过滤，因此渐进加载后需要补充“远端匹配任务请求”但不改变现有过滤显示逻辑。

### 默认首页

后台继续沿全量任务顺序读取历史页。

### 用户开始搜索或筛选

1. 立即对已加载任务执行现有客户端过滤，保证已知结果即时反馈。
2. 暂停或降级默认历史队列，把当前查询条件发送到分页接口。
3. 服务端按相同规则返回匹配任务页；相关任务的元数据优先写入本地，封面缩略图进入前台队列。
4. 缩略图成功或失败后按既定规则显示任务卡。
5. 查询条件变化时，取消旧查询尚未开始的分页请求，旧响应即使返回也因查询 token 不匹配而丢弃。
6. 清空查询后恢复默认首页历史队列，从已取得的游标继续，不重复下载已缓存任务。

如果服务端过滤暂时不可用，客户端可以继续用已加载任务显示结果，并在后台顺序读取剩余页；此降级路径必须明确标记为兼容行为，不能阻塞首页。

## 9. 图片存储与缓存策略

- 继续使用 `STORE_THUMBNAILS` 保存缩略图，沿用 `CURRENT_THUMBNAIL_VERSION` 校验。
- 云端缩略图下载完成后同时写入 IndexedDB 和内存 thumbnail cache，并通知订阅者。
- 不因分页而调用 `getAllImages`，避免把所有原图读入内存。
- `initStore` 现有孤立图片清理需要延迟到完整云端分页收敛之后，或改为只清理已经确认不再被完整任务集合引用的本地图片；不能在只拿到第一页时删除旧任务仍引用的图片。
- 云端图片元数据 map 在本轮同步期间保留全部已知条目；对未分页到的原图，详情打开时如果元数据缺失，远端 loader 继续使用响应头 MIME 类型，并在成功后补充可用元数据。
- 用户清空云端数据的 `cloudDataClearedAt` 语义不变。收到更高时间戳时，客户端清空本地图片并重新开始分页；不能在分页中间继续使用旧缩略图。

## 10. 兼容性与迁移

- IndexedDB schema 不需要新增 object store，预计不需要提升 `DB_VERSION`。
- 服务端继续支持旧版全量 snapshot 客户端；新客户端优先尝试分页协议，收到不支持的协议响应时回退到现有全量同步，保证旧部署可用。
- 回退只作为兼容路径，不应在支持分页的服务端上默认触发。应通过明确的 `protocolVersion` 或 `404/400` 判断，而不是吞掉所有网络错误后重复请求。
- 现有云端快照格式不变，分页只是读取方式变化；最终仍通过现有全量 `PUT /cloud-api/snapshot` 写回。
- 新增的客户端分页进度、失败重试和当前查询 token 属于运行时状态，不进入 `PersistedAppState`，避免改变 IndexedDB/localStorage 持久化格式。
- 原有 `/cloud-api/images/:id` 原图和 `/thumbnail` 缩略图接口不改路径和认证要求。

## 11. 错误处理与安全

- 所有新增 fetch 都沿用 `credentials: 'include'`，不把访问令牌写入 URL、日志或客户端持久化状态。
- 服务端严格校验 `limit`、`revision`、游标、过滤参数和任务分页排序，过滤无效时返回 `400`。
- 服务端分页响应不返回原图数据，减少误传敏感内容和响应体大小。
- 客户端不因单页或单图失败而清空当前已有任务；只有确认 revision 失效时才丢弃本轮未完成分页并从新基线重来。
- 认证失效时停止新请求并保留本地已加载数据，沿用当前登录状态处理，不循环重试 401。
- 页面卸载、组件卸载或 `stopCloudSync` 时取消/标记失效的分页任务，避免旧请求回写新会话状态。
- 服务端继续使用参数化 SQLite 查询和已有图片 ID 校验；新分页代码不得把查询字符串直接拼进 SQL。

## 12. 测试设计

### 单元测试

扩展 `src/lib/cloudSync.test.ts`：

- bootstrap 只应用最新 20 个任务，不等待后续页或任何原图。
- 第一页任务在缩略图请求尚未返回时已经写入 Zustand。
- 第一页缩略图逐张完成时，对应订阅者收到更新。
- 后续任务按封面缩略图完成逐张加入；一张失败不会阻塞下一张，失败任务显示占位状态。
- 原图接口在启动阶段不被预取，详情按需 loader 仍能正常读取。
- 分页期间本地新增、修改、删除不会被局部任务页生成 tombstone 或覆盖。
- 全部页完成后才允许一次完整 snapshot push。
- revision 变化会放弃旧游标并从 bootstrap 重试。
- 最终 snapshot 冲突仍沿用现有合并重试。
- 已缓存的缩略图不会重复请求。

扩展 `src/lib/imageCache.test.ts`：

- 云端缩略图写入后会更新内存缓存并通知订阅者。
- 同一图片的首屏和后台请求共享一个在途任务。

- 失败重试遵守次数和退避边界。

## 13. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 分页期间全量 push | 未加载历史被误删 | 分页完成前禁止 push，最终使用完整基线合并 |
| 缩略图写入但卡片不刷新 | 页面停留占位图 | 统一“持久化 + cache + notify”入口，并测试订阅 |
| 服务端和客户端过滤不一致 | 搜索结果遗漏或多出 | 固定 fixture 做跨端结果一致性测试 |
| revision 在翻页期间变化 | 任务重复或顺序不一致 | 游标绑定 revision，变化时从 bootstrap 重启 |
| 初始化孤立图片清理过早 | 旧任务图片被误删 | 延迟清理到完整任务集合确认之后 |
| 后续单图请求占满带宽 | 影响图片生成和交互 | 首屏/前台/后台分级队列和并发上限 |
| 新服务端未部署分页接口 | 新客户端无法启动同步 | 保留全量协议并对明确的不支持响应回退 |

## 14. 实现文件范围

## 15. 验收标准

- 新浏览器首屏不等待全量缩略图或原图，20 个最新任务卡片在分页首包应用后即可出现。
- 首屏卡片的缩略图按完成顺序独立更新；单张失败不会阻塞其他卡片。
- 第 21 个及之后的任务逐个进入首页，失败任务仍保留提示词卡片和占位图。
- 原图在启动和后台历史加载阶段请求数为零；用户打开详情、下载或复用时仍可按需取得原图。
- 搜索、状态筛选和收藏夹能优先加载尚未取得的匹配任务。
- 分页过程中不发生由局部任务集合引起的云端误删或全量覆盖。
- 旧客户端仍能使用现有全量同步接口，新客户端在分页接口不可用时有明确兼容回退。
- `npm run build` 和 `npm test` 实际通过，且新增测试覆盖上述关键行为。
